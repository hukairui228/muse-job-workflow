部署入口

解压整个包。把 部署 Prompt 连同本页交给执行端。复制 配置模板，填写自己的目标地区、时区、职能、可接受远程区域和雇主名单。简历、事实资料和历史申请由接收方在自己的私有工作区补齐。

  1. 部署在拥有所需连接器和浏览器权限的常驻环境。分别建立扫描任务、单一投递执行端和只读监督任务；检查已有任务 ID 后再注册，避免双写。模板的 09:00／17:00 与两小时监督可改，使用 IANA 时区。
  2. 目录按 runs/<run-id>/ 保存每轮快照、覆盖清单、官网证据、交接收据和断点。申请台账及材料使用独立访问权限。调度器加互斥锁，上一轮未完成则按原游标续跑。启动前先跑手动一轮；生产提交开关默认关闭。
  3. 扫描任务只负责发现、证据和派单。Muse 或替代 Harness 负责表单。监督任务读取回执和卡点，反馈给同一执行端。工作台、浏览器会话和凭据库的宿主都可单独替换。

岗位扫描

按官方安装说明安装 Agent Reach。先从公开 Web 搜索和实际站内列表开始；需要登录的渠道先读 doctor 的 active_backend，由接收方在自己的专用浏览器登录。若出现限流、验证或权限拦截，保留断点和恢复条件。

agent-reach channels
agent-reach doctor --json
agent-reach web search "entry level analyst CITY" --limit 5
agent-reach linkedin jobs "junior analyst" --location "CITY" --limit 5
agent-reach read "$OFFICIAL_JOB_URL"

LinkedIn 是可选渠道。若需要，按渠道说明执行 agent-reach add linkedin。安装说明和渠道命令以当前版本为准。

队列与投递

为接收方部署一个私有工作台，可用现有数据库加管理页。扫描端按批次增量写入，执行端认领并推进，监督端只读。以「雇主或 ATS 租户＋官方 Req」为首选唯一键，缺 Req 时使用规范化官方岗位 URL。状态变更带 revision，保留人工跳过与历史提交，写入后回读。

  "jobs": [{
    "employer": "Example Employer", "reqId": "REQ-DEMO-001",
    "officialUrl": "https://example.com/careers/req-demo-001",

  1. 在现有 Muse 主会话或受支持队列交接批次和证据引用。通过连接器或既有浏览器桥接时，核对接收方的会话绑定、主机权限、已发送正文和实际接收。连接失败时保存草稿及送达状态，恢复后先查是否已接收再重发。
  2. Muse 按 Req 独占认领，检查雇主申请限制、既有草稿和提交记录。准备真实的简历和可选求职信，复用批准过的材料与候选人提供的事实。Simplify 可作为表单辅助。逐项核对答案、附件和目标 Req 后按接收方授权提交。
  3. 保存确认页、申请编号或可核实的雇主状态。记录 submitted、submission_unconfirmed、awaiting_candidate 或 technical_block 等实际状态。提交未确认先查 Candidate Home、确认邮件或既有草稿，确认前暂停重试提交。
  4. 卡点记录当前阶段、最近动作及时间、证据、负责人和恢复条件。真正需要本人时，提供已核实的入口、正确会话／窗口、剩余动作和恢复方式。其余 Req 继续。监督分开统计列表覆盖、官网核验、执行端接收和雇主确认。

Chrome 授权

历史流程中有两份本地扩展。Muse Auto-Approve 处理 Muse 的权限卡，可选择单次或持久批准。Muse Auto-Grant 另覆盖部分连接器 OAuth 同意页和上传卡。这里的上传卡属于 Muse Browser 工具授权。Chrome 本机配置和 Muse 远端执行浏览器的授权分别验收。

  1. 在接收方单独的 Chrome profile 连接 Muse。通过 chrome://extensions 检查现有浏览器桥接扩展和站点权限；在绑定后列出会话，再对 Muse 主会话做一次只读核验。
  2. 部署时使用 Muse 原生权限。首次申请在界面核对站点、动作、文件或账号后由本人批准。平台支持持久授权时，由本人按明确的单站点、单动作范围设置，并复测是否生效。OAuth、密码填写、MFA、系统权限各自使用对应的授权界面。
  3. 若按钮要求选账号或密码而无法批准，先分辨是工具权限、保存凭据选择，还是雇主登录验证。核对发卡来源、目标、已核账号和授权通道。记录真实卡点并保留原草稿。

分享包中的 Chrome 步骤使用原生授权；历史扩展源码和安装包留在原工作区。

外部密码库

原流程采用独立凭据站点，工作台只保留申请状态和必要的私有证据引用。接收方可选托管密码管理器，或在自己的域名独立部署 Bitwarden。此处用自托管路径说明如何新建外部站点。
Bitwarden 官方 Linux 部署步骤 · 自托管选项

  1. 在接收方主机上配置私有域名、DNS、HTTPS、部署和备份。按官方指南设置接收方自己的安装配置。启用管理员与账户 MFA，限制注册及管理访问。使用官方客户端和受支持的登录入口；生成密钥和恢复材料后单独保管。
  2. 新建隔离的求职凭据库或集合。接收方在密码管理器中新增账号，设置精确的 HTTPS origin 匹配。同一雇主有多个账号时，用已核实的用户名或邮箱明确选定。同一 Workday 父域下的不同雇主保持独立条目。库中无记录时查原申请和注册历史，再决定官方登录、恢复或注册路径。
  3. 在实际执行浏览器连接其原生 Secure Store 或受支持的密码管理器。先检查该通道可见的唯一凭据、站点授权和实际自动填充。远端浏览器接不进外部库时，保留外部库的人工使用能力，按产品支持路径重新授权原生存储；该 Req 暂停自动登录，其他申请继续。
  4. 保存或更新后，核对记录 ID、准确域名和更新时间。用接收方授权的账号在独立新会话做两次登录，核到正确账号的登录后页。分别记录会话复用和新会话登录。做一次备份恢复演练，日志仅记录必要的元数据和结果。

独立部署自有凭据服务时，验收覆盖逐用户访问隔离、传输与静态加密、密钥独立保管、会话过期、日志脱敏、无缓存和备份恢复。申请台账、Prompt、日志和交接包中禁止存放密码、验证码、Cookie、会话令牌或恢复密钥。

覆盖与官网一条真实来源到末页或已存边界，必需来源缺失时 gate 失败。一个候选拿到完整 JD 和官网开放证据。

投递与恢复模拟超时后先查官方结果，提交未确认状态不会计为成功。草稿与本人卡点可以接续。真实投递须在授权范围内另行启用。
